# Cover page configuration

[`cover-page.yaml`](../cover-page.yaml) defines the shared cover page used by templates that have the cover page
enabled. You can keep the supplied definition unchanged when deploying the service. It contains display text and
generation instructions, not credentials or project-specific values to fill in manually.

The definition has three parts: `metadata` reads project information from DSW, `history` displays named project
versions, and `sections` describes additional content generated by AI from questionnaire answers.

## Loading and enabling the cover page

In the active `config.yaml`, `files.cover_definition_path` points to the definition:

```yaml
files:
  prompts_path: "prompts.yaml"
  cover_definition_path: "cover-page.yaml"
```

The cover definition path must be relative. Put the file at that path relative to the active configuration file,
and make it available to the service in the deployed environment. The loader first checks that location, then
falls back to the working directory and its `jsons` subdirectory.

The service loads the definition during configuration loading; restart the service after changing it. The file
is required even if none of your templates enable a cover page. Including the cover page in a document is controlled
by the template's cover page setting (`has_cover_page` in the API), not by removing the configuration file.

## Definition reference

Keep the top-level `version`, `metadata`, `history`, and `sections` keys. The tables below describe the shape used
by the renderer and preview API. Unless explicitly described as optional, keep the listed fields present.

### Version and identifiers

`version` is a string identifying the cover definition, for example `"1"`. It is stored with a template when that
template is created or updated with the cover page enabled. It does not select an archived YAML file or automatically
migrate existing templates.

`id` values are internal identifiers, not displayed labels or paths into questionnaire data. Keep them stable when
changing display text. Use distinct IDs for sibling elements and unique field IDs across all generated sections:
section field labels are collected into a dictionary keyed by their IDs.

### Metadata

Metadata is rendered directly from resolver results, without AI generation, in the order of `metadata.fields`.

| Field | Meaning |
| --- | --- |
| `metadata.title.id`, `metadata.title.text` | Identifier and displayed document heading. |
| `metadata.columns` | Exactly two column definitions, each with `id` and `text`: the field-label column followed by the value column. |
| `metadata.fields[].id` | Identifier of the metadata row. |
| `metadata.fields[].label` | Displayed row label, such as `Project Name`. |
| `metadata.fields[].resolver` | Supported resolver identifier that supplies the actual value; see the list below. |
| `metadata.fields[].preview` | Placeholder shown in the template preview, not a default value for generated documents. |
| `metadata.attribution` | Text placed after the metadata table. Use an empty string if no attribution text is wanted. |

The title, column headings, labels, and attribution are taken from the YAML as written; they are not automatically
translated to the selected document language. Missing metadata values produce empty cells, not the preview text.

### Supported resolvers

A `resolver` is the name of a function supported by the service, **not an arbitrary JSON path**. Adding a new name
to YAML does not add a data source; that requires implementing a resolver in the service. Unknown names are rejected
when configuration is loaded.

| Resolver | Value | Use |
| --- | --- | --- |
| `questionnaire.project_name` | The questionnaire's `name`. | Metadata |
| `questionnaire.knowledge_model` | Knowledge model package name and version, with its `organizationId:kmId:version` identifier when available. | Metadata |
| `questionnaire.project_phase` | Phase title looked up in the knowledge model using the questionnaire's `phaseUuid`. | Metadata |
| `questionnaire.created_by` | Comma-separated names of project members whose permissions contain `EDIT`; this is not necessarily the person requesting generation. | Metadata |
| `system.generated_on` | Generation date in the service's local timezone, formatted as `DD.MM.YYYY`. | Metadata |
| `static.empty` | An empty string. | Metadata |
| `project.versions` | Named project versions sorted by `updatedAt`, newest first. | History |

Use string-valued resolvers for metadata and `project.versions` for history, whose renderer requires a list.

### History

The history table uses DSW project versions, not previous AI generation runs or the YAML definition's `version`.

| Field | Meaning |
| --- | --- |
| `history.id` | Identifier of the history block. |
| `history.title.id`, `history.title.text` | Identifier and displayed history heading. |
| `history.resolver` | `project.versions`, which supplies the rows. |
| `history.columns[].id` | Identifier of the column. |
| `history.columns[].text` | Displayed column heading. |
| `history.columns[].value_key` | Key to read from each version object. The supplied definition uses `name`, `updatedAt`, and `description`. |
| `history.columns[].formatter` | Optional formatting mode, defaulting to `text`. Use `date` to format an ISO date/time string as `DD.MM.YYYY`. |
| `history.preview` | Description shown in the template preview instead of actual version rows. |

Columns appear in YAML order. Missing values produce empty cells. If a date string cannot be parsed, it is displayed
as supplied. When no versions are available, the generated document still contains the history heading and table
headers, but no data rows.

### AI-generated sections

`sections` describes cover content that participates in question assignment and AI generation. In the supplied
definition, the `Projects` section asks for project details from questionnaire answers. These sections follow the
metadata and history tables, before the main document body.

| Field | Meaning |
| --- | --- |
| `sections[].id` | Identifier of the section. |
| `sections[].title` | Section title used by the generation pipeline and shown in the preview. |
| `sections[].content` | Instructions for assigning relevant questions and generating the section from their answers. |
| `sections[].preview` | Explanatory text shown in the preview; it does not supply document content or generation instructions. |
| `sections[].fields[].id` | Identifier used to collect the field's label for generation. |
| `sections[].fields[].label` | Field label shown in the preview and supplied to the AI as a label to preserve. |

Section fields do not have resolvers and do not map directly to questionnaire question IDs. Their labels guide
generation; they do not enforce a fixed output schema or guarantee that every field appears. Put requirements about
which information to include and how to handle unanswered questions in `content`. The supplied instructions ask the
AI to use only questionnaire answers. Shared cover generation instructions also exist under
`cover_page_generation.instruction` in [`prompts.yaml`](../prompts.yaml).

## Changes to existing templates

Metadata and history rendering, and the template preview, use the currently loaded definition. Cover sections are
also copied into each template when it is created or updated with the cover page enabled. Editing this file or
incrementing `version` alone does not update those stored sections.

Coordinate structural section changes with updates to existing templates: the current implementation uses the
number of sections in the loaded definition to separate cover sections from the document body. Changing that count
while older templates still contain a different cover structure can misidentify document sections. There is no
automatic migration of stored templates based on `version`.
